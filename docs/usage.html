1. 安装#

要求 Node.js ≥ 18（服务本体只依赖 @modelcontextprotocol/sdk 和 zod）。

bash
git clone https://github.com/3810220770/bili-open-mcp-bilibili-mcp-server.git
cd bili-open-mcp-bilibili-mcp-server
npm ci

跑一遍自检，四条命令各有分工：

bash
npm run selftest      # 起服务 → 逐个调 19 个工具 / 资源 / 提示 → 生成代码还要过编译
npm run audit         # 11 类数据一致性检查（文档 ↔ 结构化数据是否对得上）
npm run check-config  # 用一份真实的 opencode 项目配置拉起服务，验证客户端侧能连上
npm run build         # 从 Markdown 重新生成 data/*.json 与 llms.txt

期望结尾：

text
tools(19):
  bili_quickstart
  …
===== resources OK: bili://catalog | templates: bili://doc/{ref} | prompts: integrate-bili-api =====
===== catalog / doc 资源 + prompt OK =====
ALL SELFTEST PASSED

npm run audit 期望：AUDIT PASSED — 11 类检查全部通过。

自检是只读的：主站写操作全部指向临时 jar，跑完会校验 secrets/cookies.json 没被动过。

不想 clone 也可以只要那个单文件：服务本体是 src/server.mjs + 同目录 7 个模块，data/ 是数据。

2. 接入 MCP 客户端#

服务入口固定是 stdio：

text
node <仓库路径>/src/server.mjs

data/ 是相对脚本解析的，与启动目录无关； secrets/ 的查找顺序是 显式参数 → 环境变量 → 包目录 → 启动方 cwd（见 §3.4）。

下面所有配置里的 C:/path/to/bili-open-mcp 都要换成你自己 clone 的实际路径。

%APPDATA%\Claude\claude_desktop_config.json

json

      "command": "node",

2.5 OpenCode#

项目级 opencode.json（只对该项目生效，推荐）：

json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "bili-open": {
      "type": "local",
      "command": ["node", "C:/path/to/bili-open-mcp/src/server.mjs"],
      "enabled": true,
      "timeout": 60000,
      "environment": {
        "BILI_CLIENT_ID": "",
        "BILI_APP_SECRET": "",
        "BILI_ACCESS_TOKEN": ""
      }
    }
  }
}

字段来自 https://opencode.ai/config.json 的 McpLocalConfig：type 必填 "local"， command 必填字符串数组，可选 cwd / environment / enabled / timeout （默认 5000ms，本服务建议 60000 —— 上传、长连、批量检索会超 5 秒）。

全局配置在 %USERPROFILE%\.config\opencode\opencode.json，把 mcp 那段合并进去。

一个坑：command 用相对路径时，服务会以该项目的目录为 cwd 被拉起。 本服务已把 secrets/ 升级为包目录优先查找，所以凭据放在包目录下不受影响； 要绝对确定，就给 BILI_COOKIE_FILE / BILI_CRED_FILE 填绝对路径，或在配置里显式给 cwd。

2.6 其他客户端#

任何支持 MCP stdio 的客户端都行，本质就是"启动 node src/server.mjs，收发 JSON-RPC"。 Windsurf / Cline / Roo Code / Continue 的字段名可能是 mcpServers 或 mcp.servers，语义一致。

3. 凭据：两套体系，别混#

这是本项目最容易踩的坑。开放平台和主站 Web 是两套完全独立的认证：

开放平台主站 Web
用什么client_id + app_secret + access_token浏览器 Cookie（SESSDATA / bili_jct）
从哪来open.bilibili.com 控制台，需实名认证 + 开发者入驻浏览器登录 bilibili.com 后导出 cookie
认证方式HMAC-SHA256 签名（x-bili-* 头 + access-token）直接带 Cookie 头（POST 补 csrf）
存哪secrets/open-platform.json（BILI_CRED_FILE）secrets/cookies.json（BILI_COOKIE_FILE）
工具bili_api_* / bili_oauth / bili_upload_planbili_cookie / bili_web_call

Cookie 里永远没有 client_id / app_secret / access_token —— 这三个不是 cookie， 任何 cookie 导出插件都拿不到。反过来，SESSDATA 也换不来开放平台的 access_token。两边不能互填。

3.1 拿开放平台凭据#

  1. 登录 https://open.bilibili.com → 实名认证
  2. 完成开发者入驻
  3. 应用管理 → 创建应用，类型选「网页应用」
  4. 授权回调域填一个你能接住的地址，例如 http://127.0.0.1:8848/callback
  5. 记下 Client ID 与 Secret
  6. 一键跑完授权回环（自动起本地服务抓 code → 换 token → 落盘）：
bash
npm run login -- --client-id <ClientID> --secret <Secret>

跑完 secrets/open-platform.json 里就有 accessToken 了，bili_api_call 立刻能发真实请求。

不用命令行也行，直接对 AI 说：

text
bili_oauth { "action": "authorize-url", "gourl": "http://127.0.0.1:8848/callback" }

拿回授权链接 → 浏览器点同意 → 从回调地址里抠出 code：

text
bili_oauth { "action": "exchange", "code": "<code>" }

exchange 成功后会自动把 token 写进 secrets/open-platform.json。 refresh_token 是一次性的，续期用：

text
bili_oauth { "action": "refresh" }

授权页地址格式（来自「接入指引 / 网页应用接入」）：

text
https://account.bilibili.com/pc/account-pc/auth/oauth?client_id=<ClientID>&gourl=<urlencoded 回调地址>&state=<随机串>

gourl 与应用里配的「授权回调域」不一致会报「不合法的授权请求」。

3.2 拿主站 Cookie#

  1. 浏览器登录 https://www.bilibili.com
  2. F12 → Application → Cookies → https://www.bilibili.com
  3. 用 EditThisCookie 之类的插件导出，或手动复制

然后导入（三种格式都收）：

text
// EditThisCookie 数组
bili_cookie { "action": "import", "jar": [{ "name": "SESSDATA", "value": "…" }, { "name": "bili_jct", "value": "…" }] }

// {name: value} 对象
bili_cookie { "action": "import", "jar": { "SESSDATA": "…", "bili_jct": "…" } }

// "k=v; k=v" 字符串
bili_cookie { "action": "import", "jar": "SESSDATA=…; bili_jct=…" }

导入后马上验证：

text
bili_cookie { "action": "whoami" }

也可以用环境变量临时注入，不落盘：

bash
BILI_COOKIE="SESSDATA=…; bili_jct=…"

SESSDATA 等同于账号登录凭证，泄露它等于交出账号。 工具默认对所有凭据脱敏（SESSDATA 显示成 abcdef…wxyz [len=124]）， 只有显式传 reveal:true 才会输出原值。不要往截图、Issue、对话里贴。

3.3 环境变量总表#

变量含义备注
BILI_CLIENT_ID应用 client_id（= x-bili-accesskeyid）别名 BILI_ACCESS_KEY_ID
BILI_APP_SECRET应用 secret别名 BILI_SECRET
BILI_ACCESS_TOKENOAuth2 access_token别名 BILI_TOKEN
BILI_COOKIE_FILE主站 Cookie jar 路径覆盖默认解析
BILI_CRED_FILE开放平台凭据文件路径覆盖默认解析
BILI_COOKIE直接给 Cookie 字符串不写文件

开放平台凭据的解析顺序：显式参数 → 环境变量 → secrets/open-platform.json。 用 bili_oauth {action:"status"} 能看清每一格到底有没有、从哪来（会标 参数 / 环境变量 xxx / 文件 clientId）。

3.4 凭据文件放在哪#

查找顺序：

  1. 工具入参（bili_cookie 的 file）
  2. 环境变量 BILI_COOKIE_FILE / BILI_CRED_FILE
  3. 包目录的 secrets/<文件名>（存在就用）
  4. 启动方 cwd 的 secrets/<文件名>（存在就用）
  5. 都没有 → 用包目录的路径（写入也落在这里）

放包目录下的 secrets/ 最稳。 MCP 客户端是用它自己的项目目录当 cwd 拉起服务的， 只按 cwd 找会一直显示「文件不存在」。

bash
# 想放别处，就给绝对路径
BILI_CRED_FILE=C:/my-creds/open-platform.json
BILI_COOKIE_FILE=C:/my-creds/cookies.json

secrets/ 整个目录在 .gitignore 里。不要把它提交到任何仓库。

验签要点（最容易错的地方）：

text
1. 取收到的原始 body 字节，拼 app_secret + body 做 SHA1
2. 与请求头 x-bilibili-signature 比对
⚠ 必须用原始字节，不要重新序列化 —— 重排 key 会验签失败

平台配置回调时会先发一次校验请求：

json
{ "event": "verify_webhooks", "content": { "data": 1371848576 }, "timestamp": "2021-01-01 12:01:01" }

要原样回 {"data": 1371848576}。失败最多重试 3 次（连接超时 5s），业务侧必须幂等去重。

# 直播间长连协议（文档 #43 / #44 / #45 / #46）

## 建立流程
1. POST /arcopen/fn/live/room/ws-start  (scope LIVE_ROOM_DATA)
   → data.conn_id, data.websocket_info.wss_link[], data.websocket_info.auth_body
2. 连 wss_link[0]，第一个包必须是 OP_AUTH(7)，body = auth_body（JSON 字符串，UTF-8）
3. 每 30s 发 OP_HEARTBEAT(2)，body 为空
4. 服务端推 OP_SEND_SMS_REPLY(5) 即消息；OP_HEARTBEAT_REPLY(3) 是心跳回执

## 包头（16 字节，全大端）
  Packet Length uint32   # 含 header 的总长
  Header Length uint16   # 固定 16
  Version       uint16   # 0=body 为明文, 2=body 为 zlib 压缩
  Operation     uint32   # 见下表
  Sequence ID   uint32   # 保留字段，可忽略
  Body          bytes

完整的可跑客户端在 examples/live_ws.py（含 zlib 多包拆解）。

4.6 wbi 签名#

2023 起 /x/space/wbi/*、/x/polymer/*、/x/v2/reply/wbi/* 这些要 wbi 签名。 bili_web_call 按路径自动判断（/wbi/、/polymer/ 等命中），也可以用 wbi:true/false 强制。

算法（src/wbi.mjs）：

  1. 从 /x/web-interface/nav 的 data.wbi_img 取 img_key / sub_key
  2. 按固定重排表拼出 32 位 mixin_key
  3. 参数按字典序 → 去掉 !'()* → urlencode → 末尾接 mixin_key → md5 = w_rid
  4. 请求带上 wts + w_rid

实测：

  • /x/space/wbi/acc/info?mid=<uid> 带签名 → code:0；wbi:false → -403 访问权限不足
  • 坑：/x/space/wbi/arc/search（投稿列表）现在直接 -403，补 dm_img_list/dm_img_str/dm_img_inter 三件套也没用；旧路径 /x/space/arc/search 仍然 code:0 可用

6. 报错与排查#

现象原因处理
客户端里看不到工具路径写错 / Node < 18 / 没重启客户端node src/server.mjs 手动起一次；npm run selftest；完全退出客户端再开
一直显示「凭据文件不存在」客户端用它自己的项目目录当 cwd把 secrets/ 放在包目录下（本版已支持），或给 BILI_CRED_FILE 绝对路径
bili_api_call 返回 4002 签名异常secret 不对 / 时间戳偏移 / body md5 与实际 body 不一致用 bili_api_sign 对照待签名串，逐行比
返回 -352风控降低频率、加设备指纹 cookie；不要重试轰炸
返回 -509 / 12019请求过于频繁退避重试（指数），并发降到 1
返回 -111csrf 失败bili_jct 过期，重新导入 cookie
返回权限错误应用没申请该 scopebili_scopes { "ref": "…" } 查需要哪个，去控制台申请
-403 访问权限不足（主站 wbi）漏了 wbi 签名别关 wbi，或看 §4.6 的路径现状
Webhook 验签一直失败重新序列化了 body用原始字节，字段顺序不能动
长连收到乱码Version=2 是 zlib按 Packet Length 循环拆包后分别解压
bili_upload_plan 说分片，实际失败分片走的是 openupos 裸二进制不要加签名头，用 url 上的 upload_token
投稿 code 非 0 但说不清分区分片等限制bili_quickstart 有投稿技术限制一节

通用第一步：任何报错都先 bili_error_lookup { "code": "<code>" }。
