bili-open-mcp — 哔哩哔哩 / B站 MCP Server#

关键词：哔哩哔哩 MCP · B站 MCP · bilibili MCP · bilibili MCP server · 哔哩哔哩开放平台 · bilibili open platform API · Model Context Protocol · MCP 工具 · AI 调用 B 站接口

记这个就行：bili-open-mcp —— 一个让 AI 直接检索、直接调用哔哩哔哩开放平台的 MCP 服务。

wbi 签名#

2023 起 /x/space/wbi/*、/x/polymer/*、/x/v2/reply/wbi/* 这些要 wbi 签名。 bili_web_call 按路径自动判断（wbi:true/false 可强制），做的是：

  1. 从 /x/web-interface/nav 的 data.wbi_img 取 img_key / sub_key
  2. 按固定重排表拼出 32 位 mixin_key
  3. 参数按字典序 → 去掉 !'()* → urlencode → 末尾接 mixin_key → md5 = w_rid
  4. 请求带上 wts + w_rid

实测：/x/space/wbi/acc/info?mid=<uid> 带签名 code:0，wbi:false 则 -403 访问权限不足。

顺带一个坑：/x/space/wbi/arc/search（投稿列表）现在直接 -403，补 dm_img_list/dm_img_str/dm_img_inter 三件套也没用；旧路径 /x/space/arc/search 仍然 code:0 可用。

举报#

两个入口，别混：

报什么接口关键参数
用户（资料/稿件/评论/动态/私信/专栏）POST /x/space/reportmid + reason + scene + tag_version
单条评论POST /x/v2/reply/reporttype + oid + rpid + reason

/x/space/report —— 按 mid 举报，body 是 urlencoded，csrf 自动带：

json
{ "mid": 3546657551551003, "reason": 5, "scene": 1, "tag_version": 1 }

scene 与 reason 的合法组合由 GET /x/space/report/options 决定（以它返回的为准，别写死）：

reason含义可用 scene
5传播色情/赌博/垃圾广告资源、诱导交易1,2,3,4,5,6,7
1色情低俗1,2,3,4,5,6,7
4引战、人身攻击1,2,3,4,5,6,7
3违法违禁行为1
2虚假不实信息1
scene含义
1用户资料（头像、签名、昵称）
2稿件
3评论
4动态
5私信
6专栏
7其他（收藏夹、播单等）

tag_version 也取自 /options（当前为 1）。

前端（space.bilibili.com 的 index-*.js）里就是这么调的：

js
IC = ({mid, scene, reason, specific_reason, specific_reason_v2, tag_version}) =>
  Re.request({ url: "/x/space/report", method: "POST",
    headers: {"Content-Type": "application/x-www-form-urlencoded"},
    data: {mid, reason, scene, specific_reason, specific_reason_v2, tag_version} })

specific_reason / specific_reason_v2 没值时 axios 会丢掉，所以最小 body 是 mid=<uid>&reason=<一位数>&scene=<一位数>&csrf=<32> —— 实测 75 字节。

/x/v2/reply/report —— 报单条评论，需要 oid（稿件 aid）+ rpid：

text
reason: 0其他 1垃圾广告 2色情 3刷屏 4引战 5剧透 6政治 7人身攻击 8内容不相关 9违法违规
        10低俗 11非法网站 12赌博诈骗 13传播不实信息 14怂恿教唆 15侵犯隐私 16抢楼 17青少年不良

返回 12008 已举报过 / 12019 举报过于频繁 / -509 请求过于频繁 / -111 csrf 失败。 注意这个接口风控更紧，静默调用常见 -352。

拿 oid/rpid 的路子（都已实测）：

要什么调用
某人的动态列表/x/polymer/web-dynamic/v1/feed/space?host_mid=<uid>（wbi）→ id_str
动态正文/x/polymer/web-dynamic/v1/detail?id=<id_str>（wbi）
某人的投稿/x/space/arc/search?mid=<uid>&ps=20&pn=1（旧路径，可用）→ aid/bvid
稿件评论区/x/v2/reply/wbi/main?oid=<aid>&type=1&mode=3（wbi）→ rpid

Cookie 存在 secrets/cookies.json（已在 .gitignore 里），路径可用 BILI_COOKIE_FILE 覆盖； 也可以直接 BILI_COOKIE="SESSDATA=…; bili_jct=…" 用环境变量注入。 SESSDATA 是账号凭证，工具默认脱敏输出，reveal:true 才显示原值。

两套凭据，别混#

开放平台主站 Web
用什么client_id + app_secret + access_token浏览器 Cookie（SESSDATA/bili_jct）
从哪来open.bilibili.com 控制台 → 应用管理（需实名 + 开发者入驻）浏览器里登录 bilibili.com 后导出 cookie
认证方式HMAC-SHA256 签名（x-bili-* 头）直接带 Cookie 头
存哪secrets/open-platform.json（BILI_CRED_FILE）secrets/cookies.json（BILI_COOKIE_FILE）
工具bili_api_* / bili_oauth / bili_upload_plan …bili_cookie / bili_web_call

Cookie 里没有 client_id / app_secret / access_token —— 这三个不是 cookie，任何 cookie 导出都拿不到。 反过来，SESSDATA 也换不来开放平台的 access_token。两边不能互填。

补上开放平台凭据#

bash
# 1. 去 open.bilibili.com 登录 → 实名认证 → 开发者入驻 → 应用管理 → 创建「网页应用」
#    授权回调域 填 http://127.0.0.1:8848/callback
# 2. 一键跑完授权回环（自动抓 code、换 token、写入 secrets/open-platform.json）
cd C:/path/to/bili-open-mcp
npm run login -- --client-id <ClientID> --secret <Secret>

跑完 bili_api_call {ref:"#5"} 就能发真实请求了。

凭据解析顺序：显式参数 → 环境变量 → secrets/open-platform.json。 用 bili_oauth {action:"status"} 可以看清每一格到底有没有、从哪来。

授权页 URL 格式（来自「接入指引 / 网页应用接入」，2025-03 新版页面）：

text
https://account.bilibili.com/pc/account-pc/auth/oauth?client_id=<ClientID>&gourl=<urlencoded 回调地址>&state=<随机串>

gourl 与应用里配的「授权回调域」不一致会报「不合法的授权请求」。 bili_oauth {action:"authorize-url", gourl:"…"} 会自动拼好并编码。

ref 接受 #12、12、012、文档 uuid、标题片段、接口 URL。

凭据#

环境变量说明
BILI_CLIENT_IDclient_id（= x-bili-accesskeyid），别名 BILI_ACCESS_KEY_ID
BILI_APP_SECRETapp_secret，别名 BILI_SECRET

凭据文件放在哪：secrets/cookies.json 与 secrets/open-platform.json 按 显式参数 → 环境变量 → 包目录 → 启动方 cwd 的顺序解析，写入固定落在包目录。 放包目录下的 secrets/ 最稳 —— MCP 客户端是用它自己的项目目录当 cwd 拉起服务的， 只按 cwd 找会一直显示「文件不存在」。要放别处就给 BILI_COOKIE_FILE / BILI_CRED_FILE 绝对路径。

无凭据时文档类工具照常工作，bili_api_sign 会用占位值演示签名结构， bili_api_call {dryRun:true} 能看完整请求。完整的能力对照表见 USAGE.md §0。
