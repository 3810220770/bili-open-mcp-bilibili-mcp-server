AGENTS.md — 给 AI 的使用契约（详细版）#

本目录是哔哩哔哩开放平台的 MCP 服务 + 结构化接口库 + 可运行示例。

第一原则：不要凭记忆猜 B 站开放接口。 一切以本仓库的 data/ 与仓库根目录的 *.md 为准。 文档没写的字段不要编，不确定就在回答里标「文档未说明」。

文档地图：USAGE.md 是给人看的操作手册（安装、接入各客户端、19 个工具的入参与真实输出、报错排查表）； 本文件是给你（AI）的契约与决策树；DISCLAIMER.md 是接口来源、能力边界与免责条款。 用户问「怎么装 / 怎么接 / 这个工具怎么用 / 报错怎么办」→ 直接引 USAGE.md 的对应小节。

接口来源与凭据：本项目调用的接口全部是官方公开提供的（开放平台文档 / 开放平台域名 / 主站 Web 接口 / 官方直播间长连），不含私有或绕过鉴权的实现。凭据由使用者自备：没有 BILI_COOKIE_FILE （secrets/cookies.json）→ bili_cookie / bili_web_call 不可用；没有 BILI_CRED_FILE （secrets/open-platform.json）→ 开放平台那套接口不可用；两者都没有时只剩文档检索、错误码、 代码生成、沙盒 mock 与签名演示。详见 DISCLAIMER.md。

凭据文件位置：secrets/ 的解析顺序是 显式参数 → 环境变量 → 包目录 → 启动方 cwd， 写入固定落在包目录。MCP 客户端是用它自己的项目目录当 cwd 拉起服务的 —— 用户说「凭据文件不存在」时，让他把文件放到包目录的 secrets/ 下，或给 BILI_COOKIE_FILE / BILI_CRED_FILE 绝对路径（详见 USAGE.md §3.4）。 不要因为读不到凭据就断定用户没配，先确认路径。

2. 核心概念#

名称含义出处
client_id应用标识，即签名头 x-bili-accesskeyid申请应用时分配
app_secret应用密钥，HMAC 的 key；只用于签名，不随请求发送同上
access_token用户授权的访问凭证，放 access-token 头，有有效期OAuth2 换取
refresh_token续期令牌，一次性的，用过即废OAuth2 换取
scope接口权限点，如 ARC_BASE；应用要申请、用户要勾选每篇接口文档首行
open_id「开发者 × 应用」维度唯一的用户 ID，替代 uid 外显（合规）用户接口返回
union_id同一开发者下多应用通用的用户 IDPOST /user/account/union_id
midB 站用户 uid，部分接口用它，注意 127003「缺少 mid 或 mid 不匹配」—
biz_code业务线标识，部分投稿接口的权限按 biz_code 配置#15
upload_token文件上传预处理拿到的凭证，后续分片/合片/提交都靠它#8

  "totals": { "docs": 170, "api": 95, "withBodyParams": 71, "withResponseParams": 72 },

      "title": "视频稿件提交",       // 取自目录名（官方接口名）
      "h1": "…",                    // 仅当文档内 H1 与目录名不同时才有
      "file": "012_视频稿件提交.md",
      "folder": "开放能力 / 视频稿件管理 / 服务端视频稿件投递",
      "path": "开放能力 / 视频稿件管理 / 服务端视频稿件投递 / 视频稿件提交",
      "type": "api",                // api | guide | event | protocol | multi-api | missing
      "scopes": ["ARC_BASE"],
      "signVersion": "1.0",         // 仅有：文档标注非 2.0 的接口（目前只有 #16）
      "url": "https://member.bilibili.com/arcopen/fn/archive/add-by-utoken",
      "method": "POST",
      "endpoints": [ … ],           // 仅 multi-api
      "hints": [ … ],               // 解析时发现的坑，见下
      "summary": "调用该接口完成稿件投递 …",
      "urlParams":  [ { "name": "upload_token", "type": "string", "required": true, "desc": "…" } ],
      "bodyParams": [ { "name": "title", "type": "string", "required": true, "desc": "…" },
                      { "name": "episode_id", "type": "int64", "required": true, "desc": "…", "depth": 2 } ],
      "responseParams": [ { "name": "resource_id", "type": "string", "desc": "稿件唯一ID" } ],
      "subSchemas": [ { "title": "common_msg参考字段", "params": [ … ] } ],
      "requestExample": "curl --location …",
      "responseExample": "{ \"code\": 0, … }",
      "bytes": 2965, "lines": 93
    }
  ]
}

字段约定：

  • type：api 单接口 / multi-api 一篇多接口 / event 推送事件 / protocol 协议说明 / guide 文档。
  • title 用目录名（官方接口名）；文档内 H1 有时只是「简介」「长连说明」，不同才写进 h1。
  • 参数对象：{ name, type, required?, desc?, depth? }。
    • 每个参数都有 type（1243/1243），值按原文，可能是 string / int64 / struct / []string / array<struct>。
    • required 可能缺失（359/364 有）：文档没写「必传」列时就没有这个字段，不代表可选，不要臆测。
    • depth 仅嵌套表出现（用 ├─ / │ 画层级时），1 = 顶层字段。
  • subSchemas：请求/响应里单独展开的子结构（如 common_msg参考字段、shop_order_list结构体）， 不要把它们和主参数混在一起；bili_api_spec 会用 ## 子结构：<title> 单独列出。
  • hints：解析阶段发现的使用陷阱，例如「GET 请求但参数列在 body 参数下」「签名版本 1.0」。
  • responseParams 嵌套字段按原文写法（area.area_id_name）或 depth 表达，两种都出现过。
  • 样例文本截断到 4000 字符。

5. MCP 工具：决策树与参数#

19 个工具（17 个开放平台 + 2 个主站 Cookie/Web）。先看决策树，再看下面的逐条说明（ref 一律接受 #12 / 12 / 012 / uuid / 标题片段 / 接口 URL）。

text
第一次接触        → bili_quickstart {}
不知道接口叫什么  → bili_docs_search {query} / bili_endpoints {pathContains}
想按模块浏览      → bili_docs_list {folder|type}
要确认申请哪些权限 → bili_scopes {}
已知 ref 看参数   → bili_api_spec {ref}
看非接口文档      → bili_docs_get {ref}
要写代码          → bili_codegen {ref, lang}      ← 自己拼签名容易错
参数不确定/要校验 → bili_api_prepare {ref, query, body}
要发请求          → bili_api_sign（出 curl） / bili_api_call（dryRun → 真调）
投稿上传怎么切    → bili_upload_plan {fileSizeMB}
拿 token / 续期   → bili_oauth {action}
接消息推送        → bili_webhook {action}
做直播消息        → bili_ws_protocol {}
沙盒联调          → bili_mock {action}
主站登录态        → bili_cookie {action:"whoami"}
调主站 Web 接口   → bili_web_call {path}
报错码            → bili_error_lookup {code}

5b. 新增工具（9 个）#

bili_endpoints#

按条件过滤全部端点，比全文搜索精确。

参数说明
methodGET/POST/…
scope权限点，如 SHOP_ORDER_INFO
hostmember.bilibili.com / openupos.bilivideo.com / api.bilibili.com

sourceopen（默认，开放平台）/ web（主站隐藏能力）/ all（两边都列）

典型问法：「所有需要 SHOP_ORDER_INFO 的 POST 接口」「上传类接口有哪些」→ {host:"openupos.bilivideo.com"}。 「举报怎么调」「有哪些写操作」→ {source:"web", pathContains:"举报"}。

source:"web" 的数据来自 data/web.json：112 条主站 Web 隐藏能力（开放平台文档里没有的那些）， 每条带方法 / 完整地址 / 参数 / 返回码 / 无 Cookie 实测状态。整块读用 resource bili://web， 逐条复核用 npm run web:probe。

bili_scopes#

参数说明
无列出全部 scope 及覆盖端点数
scope该 scope 下所有端点
ref该接口的 scope，以及每个 scope 下的其它接口

bili_api_prepare#

参数说明
ref必填
query / body待校验的参数对象

做的四件事：① 按文档类型转换（"21"→21、"true"→true、"a,b"→["a","b"]） ② 列缺必填 ③ 列多传的字段（文档未列出）④ 把 GET 文档里写在 body 下的参数归到 query。 注意：它不猜测可选参数的默认值。

bili_codegen#

参数说明

langpython / node / curl / java / php / go，默认 python

生成的是可编译的骨架：完整签名实现 + 该接口全部参数（必填直接写入、可选注释掉）+ code != 0 处理。 参数值留 TODO。生成结果在 npm run selftest 里会被 py_compile / node --check 真实编译一遍。

bili_upload_plan#

参数说明

输出：单文件还是分片、片数、每片 offset 区间、part_number 起止、完整调用顺序、注意事项。 回答「这个大文件怎么传」直接用它，别自己算。

bili_webhook#

5c. 凭据：两套体系，别混#

开放平台主站 Web
凭据client_id + app_secret + access_token浏览器 Cookie（SESSDATA / bili_jct）
来源open.bilibili.com 控制台 → 应用管理（需实名 + 开发者入驻）登录 bilibili.com 后导出 cookie
认证HMAC-SHA256（x-bili-* 6 个头）直接带 Cookie 头
文件secrets/open-platform.jsonsecrets/cookies.json
覆盖变量BILI_CRED_FILEBILI_COOKIE_FILE
工具bili_api_* / bili_oauth / bili_upload_planbili_cookie / bili_web_call

client_id / app_secret / access_token 不在任何 cookie 里，导出多少次 cookie 也拿不到； SESSDATA 同样换不来开放平台的 token。

凭据解析顺序：显式参数 → 环境变量（BILI_CLIENT_ID / BILI_APP_SECRET / BILI_ACCESS_TOKEN）→ 凭据文件。 bili_oauth {action:"status"} 逐格显示「有没有 / 从哪来」。

补齐开放平台凭据#

bash
# 控制台建应用（类型选「网页应用」），回调域填 http://127.0.0.1:8848/callback
npm run login -- --client-id <ClientID> --secret <Secret>

脚本起本地回调服务 → 打印授权链接并自动打开浏览器 → 抓 code → POST 换 token → 写入 secrets/open-platform.json（accessToken / refreshToken / expires_in / scopes）。

授权页 URL（2025-03 新版，旧的 passport.bilibili.com/register/pc_oauth2.html 已停维护）：

text
https://account.bilibili.com/pc/account-pc/auth/oauth?client_id=<ClientID>&gourl=<urlencoded>&state=<随机串>
  • gourl 必须与应用「授权回调域」一致，拼接前 URL encode；不一致 → 「不合法的授权请求」
  • 回调：<return_url>?code=<code>&state=<state>
  • code 一次性、短时效；refresh_token 一次性
  • bili_oauth {action:"authorize-url", gourl:"…"} 自动组链接

5d. 主站 Web（Cookie，非开放平台）#

与开放平台是两套体系：开放平台用 client_id + secret + HMAC 签名 + access_token； 主站 www.bilibili.com / api.bilibili.com 的 Web 接口用浏览器 Cookie（SESSDATA 等）。 两边的凭证不能互换 —— 把 SESSDATA 填进 BILI_ACCESS_TOKEN 只会拿到 401/-101 —— 反过来，client_id/app_secret 也不在 cookie 里（获取方式见 5c）。

6. 请求总则#

6.1 2.0 签名（HMAC-SHA256）#

版本例外：#16 唤起粉端投稿接口说明 在文档里明确写「该接口使用的签名为 1.0」， 但其 C# Demo 只是把 SignatureVersion 填成 "1.0"，文档没有给出 1.0 的算法差异。 本仓库的签名实现只做 2.0；接 #16 前需向平台确认 1.0 的规则。data/index.json 里这条带 signVersion: "1.0"，bili_api_spec 会打上 ⚠ 标记。

参与签名的只有这 6 个头，按 key 字典序排列：

text
x-bili-accesskeyid
x-bili-content-md5
x-bili-signature-method
x-bili-signature-nonce
x-bili-signature-version
x-bili-timestamp

拼成 k:v，行间用 \n，末尾不留换行；Authorization = HMAC-SHA256(app_secret, 待签串) 的 hex 小写。

可复现的例子（secret = test_secret）：

text
x-bili-accesskeyid:93a0f774fae84e6c
x-bili-content-md5:d41d8cd98f00b204e9800998ecf8427e
x-bili-signature-method:HMAC-SHA256
x-bili-signature-nonce:1730185575446751000
x-bili-signature-version:2.0
x-bili-timestamp:1730185575

→ Authorization: 93daf316cf499f313e6e7c487857fe3b1c8e9b6a262123e36ddf867bd97e5e1f （待签串 223 字节；md5("") = d41d8cd98f00b204e9800998ecf8427e；md5('{"title":"demo"}') = 0644a83ba42a8257fe418164beb5509a）

用这两个值可以自检任何实现的正确性。

6.3 三个最常见的签名错误#

  1. md5 算错对象：必须是实际发出的字节。Python 里 md5(str(dict)) ≠ md5(json.dumps(dict))。
  2. 末尾多一个 \n，或少了某一行 → 4002 签名异常。
  3. GET 用了非空 body 的 md5：GET 没 body，x-bili-content-md5 必须是 md5("")。

6.4 无需签名的接口（唯一例外）#

分片上传 / 单文件上传（#9 / #14）走 openupos.bilivideo.com，裸二进制、不带任何 X-Bili-*， 凭 URL 上的 upload_token 鉴权，Content-Type: application/octet-stream。

7. OAuth2 完整流程#

text
① 用户在授权页同意 → 回调地址收到 code
② POST https://api.bilibili.com/x/account-oauth2/v1/token
   Content-Type: application/x-www-form-urlencoded
   client_id / client_secret / grant_type=authorization_code / code
   → { access_token, refresh_token, expires_in, scopes[] }
③ 业务请求带 access-token: <access_token>
④ 过期前用 refresh_token 续期（一次一份）
   POST https://api.bilibili.com/x/account-oauth2/v1/refresh_token
   grant_type=refresh_token / refresh_token

要点：

  • expires_in 是 UTC 时间戳（不是剩余秒数），文档样例 1630220614。
  • 每个 refresh_token 只能用一次，续期后要用返回的新 token。
  • access_token 过期后不能再刷新，必须让用户重新授权。
  • 用户主动解除授权时，平台会推 解除授权 事件（#123），要接。
  • 客户端应用走 SDK 拿 code，网站应用走重定向，两者拿到的 code 等价。

10.1 视频投稿（最常用）#

text

  • 删除稿件不可逆（123005 / #20）。
  • 技术限制：≤4GB、时长 <5h、推荐 mp4/flv、峰值码率 ≤60Mbps、分辨率 ≤4096×4096、帧率 ≤120fps、 关键帧 ≥10s、yuv420、SDR 8bit / HDR 10bit、音频 ≤320Kbps / 2ch / 48kHz。

  • 非正式会员单日限投 5 个（123036）。

Version=2 → body 是 zlib 压缩，解压后可能包含多个完整包（递归解析）。 HTTP 心跳 #45（client_id + conn_id）/ 批量 #46 是替代方案。示例见 examples/live_ws.py。

10.4 一键开播（#48–#53）#

走 /liveopen/ 前缀，流程：grantUrl 拿授权 → 用户授权 → 回调 → startLive → endLive。

10.5 消息推送 / Webhook（#121–#168，41 个事件）#

  • 在管理中心配置回调地址，保存时平台会发一次校验请求： ``json { "event": "verify_webhooks", "content": { "data": 1371848576 }, "timestamp": "2021-01-01 12:01:01" } ` 必须原样回 {"data": 1371848576}`。
  • 统一结构：{ "event": "", "content": {}, "timestamp": "" }。
  • 来源验证：x-bilibili-signature 头 = SHA1(app_secret + request body)。 校验时收到消息的字段顺序必须与文档发送格式一致，否则签名对不上 —— 建议用原始 body 字节而不是重新序列化。
  • 送达判定：返回 2xx 即视为成功；5s 超时、最多重试 3 次 → 业务侧必须幂等去重。

11. 沙盒 / 白名单 / 未列出的能力#

  • 沙盒（#169）：member.bilibili.com/mock/...，返回 MOCK 数据，不影响正式环境。 用同一套 OAuth2 流程拿到的 access_token 即可调；但应用仍须已申请对应 scope，否则返回权限错误。 注意 mock 路径与正式路径不总是一致（例：正式 /arcopen/fn/archive/video/init，mock /mock/video/part/init），以 #169 表格为准。
  • 白名单（#3）：某接口配置白名单后只有列表内 uid 能调，报 127305 白名单限制；默认关闭。
  • 未列出的功能（#170）：文档只放已有商务合作的能力；有别的需求走邮件 openplatform-feedback@bilibili.com，需写明合作内容、量化收益、公司信息、对接人。 但「文档没写」不等于「调不到」—— 主站 Web 上那一大片（举报 / 拉黑 / 动态 / 评论 / 收藏 / 历史 / 消息 / 直播 / 创作中心） 走的是浏览器 Cookie，不走 2.0 签名，已收进 data/web.json：112 条 / 17 组。 读法：bili_endpoints {source:"web"} 过滤，resource bili://web 整块读，bili_web_call 直接调。

12. 分页与字段约定#

文档里的分页字段不统一，按接口看，别套用：

字段含义
pn / page_no / page页码（page 从 0 开始，pn 默认 1）
ps / page_size / pageSize / size每页数量（上限 50 / 100 / 200 不等）
nextPageIndex下一页索引，第一页传 0

其他约定：

  • 所有 URL 参数需 URL encode，中文用 UTF-8。
  • 时间字段多为 秒级 unix 时间戳（expires_in 例外，是绝对时间戳但同样是秒）。
  • 金额字段注意单位（分 / 元）与 spec_prices 这类 sku 数组结构，必须与规格组合数一致。

13. 代码生成模板#

Python（用 examples/bili_open.py，不要另写一套）

python
import sys; sys.path.insert(0, "examples")
from bili_open import call, MEMBER_HOST

r = call("GET", MEMBER_HOST + "/arcopen/fn/user/account/info")
if r.get("code") != 0:
    raise RuntimeError(r)          # 注意: HTTP 200 也可能是业务错误
print(r["data"]["openid"])

Node（用 examples/node_client.mjs）

js
import { callApi } from "./examples/node_client.mjs";
const r = await callApi({ method: "GET", url: "https://member.bilibili.com/arcopen/fn/user/account/info" });
if (r.json.code !== 0) throw new Error(JSON.stringify(r));

生成代码时必须覆盖的点

  1. 先取 scope，确认应用已申请（否则 127007）。
  2. code != 0 要处理，别只看 HTTP 状态。
  3. 分页字段按该接口文档取，不要统一写成 page/page_size。
  4. token 刷新用返回的新 refresh_token（一次性的）。
  5. 上传类接口不加签名头。
  6. 参数在 bodyParams 但方法是 GET 时，按 query 拼到 URL（见 6.5）。
  7. subSchemas 里的字段是嵌套结构的字段，别平铺成顶层参数。

15. 不要做的事#

  • ❌ 不要凭记忆写 /x/v2/... 这种主站接口 —— 本目录只覆盖开放平台 /arcopen/fn/、/liveopen/fn/ 系。
  • ❌ 没有凭据时不要编造 access_token，也不要把占位签名当作可用请求。
  • ❌ 不要把 app_secret 写进请求体或 URL，它只用于本地计算的 HMAC。
  • ❌ 不要在 GET 请求上带 body 并据此算 md5。
  • ❌ 不要假设 mock 路径与正式路径一致。
  • ❌ 不要把 responseParams 当成完整 schema —— 省略号、嵌套对象都以原文为准，必要时 bili_docs_get 读全文。
  • ❌ 不要忽略 hints / signVersion / subSchemas —— 它们是从原文里挖出来的差异点。
  • ❌ 不要为了「补齐」而给缺失的 required 编一个值：文档没写就是没写。
